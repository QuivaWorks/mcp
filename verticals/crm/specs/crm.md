# CRM vertical

## Overview

This vertical models a sales-focused CRM on the Quiva platform. The core entities are **Company**, **Deal**, **Product** and **Activity**, with the existing **SHARED.Client** record reused for contacts/people. Deals are record configs with a `deal_stage` enum field — not tasks in a space — because deal data requires typed validation (value, probability, close date). This was ratified as a decision on 2026-08-02. Activities are record configs rather than tasks because the requirements need typed outcomes, conditional forms, and flow triggers on activity completion. A single **CRM_ACTIVITIES** space holds follow-up tasks and to-dos generated by flows. Computed fields (days_in_current_stage, expected_revenue, open_deal_value) are plain stored fields written by flows, not schema-level calculations.

**Consequence of Deal-as-record, stated plainly:** a table view is an ordered list of columns and nothing more — `ViewTableNode{Type, Columns[]{Field, Order}}` in `records-service/model/api.go:143`. There is no grouping, no default sort, no filtering, and no kanban. So the "pipeline" is a flat table of deals with a `deal_stage` column that a user eyeballs or filters by hand in the UI. That is materially weaker than the pipeline board in the rough requirements, and it is the price of choosing typed deal data.

## CRM Activities space

```yaml
category: spaces
id: CRM_ACTIVITIES
name: CRM Activities
record_config_ids: [Client, Company, Deal, Product, Activity]
statuses: [To Do, In Progress, Waiting, Done, Cancelled]
```

This space holds actionable work items: follow-up calls, proposal tasks, renewal reminders. Tasks here are created by flows when deals change stage, activities complete with a `next_action`, or lead-aging checks fire.

`record_config_ids` links these record configs to the space. `Client` is mandatory — it comes from `SHARED`, is deployed to every account carrying a vertical, and is the contact record the whole CRM hangs off. The others are listed because tasks in this space reference them.

## A note on all record-triggered flows

Four flows below trigger on records (`deal-stage-change`, `activity-completion`, `deal-rollup`, `deal-created`). The same two constraints apply to each:

- The trigger filters by `record_config_id` and `event_type` only. Any "when field X changes" logic must live in a condition node inside the flow.
- The trigger does not deliver prior record state. A flow that needs to detect a change must compare against a value it previously stored on the record.

---

## deal-stage-change flow

```yaml
category: flows
id: deal-stage-change
name: Deal Stage Change
trigger: record
```

Triggers on **every** Deal record update. A record trigger filters only by `record_config_id` and `event_type` (`hub-service/model/request.go:470`) — there is no field-level filter, so "when `deal_stage` changes" cannot be declared on the trigger.

Nor does the trigger deliver the record's prior state, so `old.deal_stage ≠ new.deal_stage` is not available. The flow must detect the change itself by comparing `deal_stage` against the last value it recorded — which is what `stage_change_date` is for. If `stage_change_date` is absent or the stage differs from the stage last stamped, treat it as a transition.

**Nodes:**
1. **condition: stage_changed** — compare current `deal_stage` against the stage recorded at `stage_change_date`; exit if unchanged.
2. **eval: set_stage_date** — set `stage_change_date` to now, reset `days_in_current_stage` to 0.
3. **condition: closed_won** — if deal_stage = "Closed Won":
   - Update linked Company: `account_type` → "Customer".
   - Create task in CRM_ACTIVITIES: "Schedule kickoff call with {deal_name}", due +3 days, assigned to deal_owner_user_id.
4. **condition: closed_lost** — if deal_stage = "Closed Lost":
   - Create task: "Post-mortem: {deal_name} lost to {lost_reason}", assigned to deal_owner_user_id.
5. **condition: proposal** — if deal_stage = "Proposal":
   - Create task: "Send proposal to {primary_contact_id}", due +1 day, assigned to deal_owner_user_id.

## activity-completion flow

```yaml
category: flows
id: activity-completion
name: Activity Completion
trigger: record
```

Triggers on Activity record update when `status` changes to "Completed".

**Nodes:**
1. **eval: set_completed_at** — set `completed_at` to now.
2. **condition: has_next_action** — if `next_action` is not empty:
   - Create task in CRM_ACTIVITIES: "{next_action}", due +2 days, assigned to `assigned_to_user_id`.
3. **condition: has_deal** — if `related_deal_id` is set:
   - Update Deal: increment `activity_count`, set `last_activity_date` to now.
4. **condition: has_company** — if `related_company_id` is set:
   - Update Company: set `last_activity_date` to now.

## deal-health-check flow

```yaml
category: flows
id: deal-health-check
name: Deal Health Check
trigger: schedule
```

Runs daily at 06:00 UTC. Iterates open deals (deal_stage not in [Closed Won, Closed Lost]).

**Nodes:**
1. **eval: calc_days** — set `days_in_current_stage` = today − stage_change_date.
2. **condition: stalled** — if days_in_current_stage > 45 AND last_activity_date < today − 14 days:
   - Set `deal_health_status` = "Stalled".
   - Create task: "Rescue stalled deal: {deal_name}", priority High, assigned to deal_owner_user_id.
3. **condition: at_risk** — else if days_in_current_stage > 30 OR last_activity_date < today − 7 days:
   - Set `deal_health_status` = "At Risk".
4. **else** — set `deal_health_status` = "Healthy".

## lead-aging-check flow

```yaml
category: flows
id: lead-aging-check
name: Lead Aging Check
trigger: schedule
```

Runs daily at 07:00 UTC. Queries SHARED.Client records. (Assumes Client has `last_activity_date` and `owner_user_id` fields or these are stored separately; if not, this flow operates on Company instead.)

**Nodes:**
1. **condition: no_activity_30** — if last_activity_date < today − 30 days:
   - Create task: "Follow up with {client name} – no contact in 30+ days", priority High, assigned to owner_user_id.
2. **condition: no_activity_60** — if last_activity_date < today − 60 days:
   - Escalate: also notify owner's manager (agent node or notification).

*Note: If SHARED.Client lacks these fields, the flow must instead query Activity records grouped by related_contact_id to derive last activity date.*

## renewal-reminder flow

```yaml
category: flows
id: renewal-reminder
name: Renewal Reminder
trigger: schedule
```

Runs daily at 06:30 UTC. Queries Company records where account_type = "Customer".

**Nodes:**
1. **eval: calc_days** — set `days_to_renewal` = contract_renewal_date − today.
2. **condition: 90_days** — if days_to_renewal between 1 and 90 (inclusive) AND no existing open task for this renewal:
   - Create task: "Schedule renewal conversation: {company_name}", due = contract_renewal_date − 60 days, assigned to primary_owner_user_id.
3. **condition: 30_days** — if days_to_renewal between 1 and 30:
   - Create task: "Final renewal push: {company_name}", priority High.
4. **condition: expired** — if days_to_renewal < 0:
   - Update Company: account_status → "At Risk".
   - Create task: "Reactivate lapsed customer: {company_name}".

## Sales Intelligence assistant

```yaml
category: assistants
id: sales-intelligence
name: Sales Intelligence
```

**Behaviour (system prompt summary):**
You are a sales intelligence assistant for the CRM vertical. You have access to Company, Deal, Activity, and Client records. Your capabilities:

1. **Deal analysis** — When asked about a deal, retrieve the Deal record plus related Activities. Report days in stage vs. typical (30 days), recent activity frequency, whether a decision-maker is engaged, and recommend next actions.
2. **Pipeline review** — Summarise the user's open deals by stage, flag any with deal_health_status = "Stalled" or "At Risk", and suggest priority order.
3. **Prospect research** — Given a company name, summarise what is known in Company records and related Deals/Clients. If external research is needed, say so.
4. **Next best action** — List overdue tasks, deals past close_date, and contacts with no activity in 30+ days. Prioritise by deal value × risk.
5. **Objection handling** — When given an objection, provide a framework: acknowledge, reframe, provide evidence, propose next step.

**Model:** `claude-sonnet-4-5`. (`llm_provider` must be `claude` or `anthropic`; the invoke handler rejects anything else.)

**Knowledge sources:** to be resolved at build time. Knowledge URIs use the `kv://`, `obj://`, `str://`, `sid://`, `dta://` schemes; which of these exposes live record data is not yet established.

**Tools:** none specified. Tool values use the `mcp://`, `fun://` or `bit://` schemes and must be resolved against `list_functions` at build time. The earlier draft named `record_list` / `record_get` / `task_list` / `task_create`; those were invented and are not known to exist.

## Out of scope

- **Kanban board / drag-drop pipeline view.** No kanban component exists anywhere in the frontend.
- **Grouped table views.** A table view is `{field, order}` columns only (`records-service/model/api.go:143`). Grouping by `deal_stage` is not expressible.
- **Default sort on a table view.** Same reason. `sortBy` / `groupBy` / `filterBy` appear nowhere in the records components.
- **Per-user filtered views (`my-deals`).** Table views carry no filter. A rep sees all deals and narrows by hand in the UI.
- **Field-level record triggers ("when deal_stage changes").** Triggers filter by record config and event type only.
- **Prior record state in a flow.** The trigger delivers the record, not a before/after pair.
- **User override of `probability_percent`.** The rough requirements said probability defaults from the stage but stays editable. A `value` rule recomputes on every change, so the two cannot coexist. Built as a `value` rule plus `readonly`: probability always follows the stage. Same applies to `expected_revenue`, `requires_approval` and `DealLine.line_total`.
- **Colour thresholds, badges, avatars, mini-charts, card designs.** UI styling is not configurable.
- **User / Team / Role record configs.** Users already exist in the platform.
- **Hierarchical labels (nested tag trees).** Tags are flat strings only.
- **Lead scoring by AI with 0–100 score auto-updated.** Could be approximated via a scheduled flow calling an agent node, but not specified here—complex and unvalidated.
- **Dashboard widgets with aggregates (pipeline value, win rate, activity counts).** No dashboard widget configuration.
- **Inline row actions, bulk actions, column toggle/reorder.** Table views define columns; interaction chrome is platform-level.
- **Approval workflow with form locking.** Flows can set `approval_status` and `requires_approval`, but cannot lock a form from editing.
- **Email sync / inbound email trigger creating Activities automatically.** Email trigger exists but wiring it to parse sender, match to Client, and create an Activity record requires custom flow logic not detailed here.
- **File attachment categories, version control, confidentiality flags.** File storage is a platform feature; no vertical config controls versioning or access levels.
- **Meeting transcription service setup.** Platform feature, not vertical config.
- **Third-party integrations (Salesforce sync, LinkedIn enrichment, Crunchbase lookup).** Not vertical configuration.
- **Complex forecasting, territory management, custom reporting dashboards.** Beyond record/flow/assistant scope.
- **Attendees array on Activity with typed objects.** JSON Schema supports arrays of objects, but form rendering of complex nested arrays is limited; modelled as free text or omitted.
- **Activity labels (multi-select with hierarchy).** Replaced by flat tags; hierarchy not supported.
- **Auto-navigation context (auto-populate contact when navigating from Contact page).** No form-context variable available.

## Open questions

- **SHARED.Client schema:** What fields does the existing Client record config include? The spec assumes `first_name`, `last_name`, `email`, `phone`, `company_id`, and `owner_user_id` exist. If `last_activity_date` or `lifecycle_stage` are needed, should they be added to Client (if mutable) or tracked via Activity queries?
- **Currency handling:** Should `deal_value` be stored in a single currency with conversion, or stored as-entered with a separate `deal_value_usd` field written by a flow? The spec assumes as-entered with no conversion.
- **Notification channels:** Flows can create tasks, but how should "notify manager" actions be delivered—email, Slack, in-app? If Slack, is the integration connected?
- **Discount approval threshold:** The spec uses 20%. Should this be configurable per account, or is a fixed threshold acceptable?
- **Activity ↔ Task relationship:** Activities are records; follow-up tasks live in CRM_ACTIVITIES space. Should completed tasks back-link to the Activity that spawned them, and if so, how (task description, metadata)?
- **Client ownership:** Is `owner_user_id` on SHARED.Client, or should contact ownership be inferred from the linked Company's primary_owner_user_id?
- **Deal ↔ Product linkage:** Products are now specified, but nothing connects them to deals. Options: a `deal_products` array of objects on Deal (simple, but nested-array form rendering is limited), or a separate DealLine record config (cleaner, more objects). Needs a decision before Deal is built, since it changes Deal's schema.
- **Assistant tools and knowledge:** Which `mcp://` / `fun://` / `bit://` tools exist for reading records and creating tasks, and which knowledge scheme exposes live record data? Must be resolved against `list_functions` before the assistant is built.
- **Pipeline usability:** With no grouping, sorting or filtering on table views, is a flat deal table acceptable, or does the pipeline need rethinking (e.g. one space per stage, or deals mirrored as tasks purely for the board)?
